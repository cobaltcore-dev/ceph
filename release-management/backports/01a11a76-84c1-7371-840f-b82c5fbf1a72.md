## Justification (public)

Clients rejected by RGW rate limiting receive no guidance on when to retry, so
they either back off far longer than necessary or hammer the endpoint until
they succeed. This backport adds a `Retry-After` header to rate-limited
responses, computed from the client's actual token deficit and replenishment
rate.

It also adds rate limiting for LIST and DELETE operations, which previously
could not be limited independently of general read and write traffic, and makes
the token bucket accumulation window configurable via `rgw_ratelimit_interval`.

dditionally, the backport fixes a bug. With rate limiting enabled but an
individual limit left at 0 (unlimited), ops tokens are still deducted per
request while never being refilled. That is harmless on its own, because the
credit isn't checked while the limit is 0. But if the operator later sets that
limit, the credit may already be far negative and recovers only at the newly 
onfigured rate, so the user can be blocked for a long time.

## Justification (internal)

Three upstream changes are part of the backport:

1. **ceph/ceph#64762** — LIST/DELETE rate limiting, `rgw_ratelimit_interval`.
2. **ceph/ceph#66509** — fixes unbounded negative ops budget.
3. **ceph/ceph#68210** — adds the `Retry-After` header itself.

PR 1. and 3. are required by the customer. 2. is needed addition to 1. because
it resolves a bug and omits merge conflicts.

## Risk notes

**Blast: availability.**
- The backport changes the request admission. A defect is more likely to change
  how traffic is accepted or rejected than to corrupt data.
- `dae572` bumps `RGWRateLimitInfo` from struct_v 1 to 2 to add `max_list_ops`
  and `max_delete_ops`. Reading old records with the new build is safe: the
  `struct_v >= 2` guards default both new fields to `0`, so v1 records decode
  and behave as before.
  The other direction is not. `compat_v` stays at `1` while the new fields are
  inserted in the middle of the field order. So an old decoder doesn't reject a
  v2 record. It reads it positionally and shifts the fields: `max_list_ops`
  ends up in `max_write_bytes`, `max_delete_ops` in `max_read_bytes`, and
  `enabled` gets the low byte of the real `max_write_bytes`. An RGW on the old
  build reading a record written with `max_list_ops = 100` applies a 100 byte
  write bandwidth limit. There is no decode error, just wrong values.
  v2 records only appear once a rate limit is written by the new build
  (`radosgw-admin ratelimit set` or the admin REST API). The upgrade itself
  does not rewrite stored records, so an upgrade without a config change
  produces no v2 data.
- Additionally, there is a minor issue the backport (`91e9f00`) introduces. If
  the user is charged for a request and the bucket rejects the request, the
  user gets the token back. The problem: it also happens if the user has
  unlimited access.
  So the amount of credits for a user can grow over time. However, it doesn't
  matter much because it's corrected by increase_tokens, min(max * 1000, …) on
  the next refill. Compared to the issue the commit is fixing, it's a minor one.

**Conflict: trivial.** `91e9f00` and `3dae903` both cherry-pick onto the branch
with no conflicts at all. Only `dae572` was cherry-picked with minor conflicts
that are documented as part of the commit message.

**Coverage: partial.**
- `91e9f00` adds four regression tests
  (`unlimited_access_not_left_large_*_ops_budget`)
- `3dae903` adds
  `TEST(RGWRateLimitEntry, compute_delay)` and updates the existing suite to
  the new `int64_t` return
- `dae572` contributed both unit and integration tests for the new admin
  options.

No test covers the refund asymmetry described above.

## Behavior change

- Rate-limited S3 responses now carry a `Retry-After` header giving the seconds
  until the client's credit recovers. The status code is unchanged, still
  `503` (Swift: `498`). Operators who need `429` must remap at the proxy layer.
- New rate limit dimensions `max_list_ops` and `max_delete_ops` can be set via
  `radosgw-admin ratelimit set` and the admin REST API. Both default to `0`
  (unlimited).
- New config option `rgw_ratelimit_interval` (default `60` seconds) controls
  the token bucket accumulation window. Previously hardcoded at 60, so it stays
  the same in case of the default value.
- Ops counters no longer accumulate unbounded debt while a limit is `0`. A user
  who would previously have been rejected for hours or days on first enabling a
  limit now starts from a clean budget.

## Upgrade notes

`rgw_ratelimit_interval` is flagged `startup`, so changing it from the default
requires an RGW restart.

Don't change any rate limit configuration until all RGWs run the new build.`RGW_ATTR_RATELIMIT` is shared state read by every RGW, radosgw-admin and the
admin REST API. A `ratelimit set` during the rollout rewrites the record as v2
and any RGW still on the old build misreads it (see Risk notes). Reads are
unaffected, so the rolling restart itself is safe, only writes create v2
records.
