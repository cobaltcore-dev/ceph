## Justification (public)

Since 19.2.6, cephadm creates daemon cephx keys with the `aes256k` key type.
The NVMe-oF gateway images for squid bundle their own librados, built before
`aes256k` existed, so a gateway cannot authenticate with such a key. It fails
to connect to the cluster and restarts. The nvmeof service never reaches its
target count.

- https://tracker.ceph.com/issues/81778

  `orch:cephadm:smoke-roleless/{0-distro/centos_9.stream_runc 0-nvme-loop 1-start 2-services/nvmeof 3-final}`,

  with `"key_type": "aes256k"`. The gateway logs `rados.IOError: [errno 5] RADOS I/O error`
  on each of 5 starts, then `Unable to create OMAP, exiting!`, and no mon ever
  sees a connection attempt. Ends in `MaxWhileTries` after 300s.

## Risk notes

- **blast: availability** — the patch changes which cephx key type cephadm
  requests per daemon (`utils.key_type_for()`). nvmeof gets the previous `aes`,
  every other daemon type keeps `aes256k`. A regression in that dispatch would
  hand a daemon a key type its image cannot use. The same failure mode this
  fixes, i.e. a daemon that will not start. No data path is touched and no
  on-disk format changes, so nothing can be silently corrupted.
- **conflict: substantive** — fully custom downstream patch, not a cherry-pick
  (rubric: "substantive conflicts requiring code change, OR fully custom"). It
  applies cleanly to the effort branch, but it carries no upstream review
  behind it; the code is new on this line.
- **coverage: partial** — new
  `src/pybind/mgr/cephadm/tests/test_nvmeof_key_type.py` (5 tests) covers the
  per-daemon dispatch, key creation and `key_rotate`. 
- **Removal condition** — `LEGACY_CIPHER_DAEMON_TYPES` has to go back to empty
  once a squid-line gateway image ships librados that understands `aes256k`.
  The 1.7 and 2.0.0 images already do, but those are tentacle-related images.
  Until that happens, every carry-forward of this patch re-applies the
  downgrade.

## Behavior change

NVMe-oF gateway daemon keys are created with key type `aes` instead of
`aes256k`. All other daemon types are unchanged, including the post-upgrade key
rotation, which only covers mon/mgr/osd/mds. `ceph orch daemon rotate-key` on a
gateway also produces an `aes` key.

This is a deliberate downgrade to a weaker cipher for one daemon type. `aes`
(`CEPH_CRYPTO_AES`) is AES-128-CBC with a fixed IV and a 16-byte key; `aes256k`
(`CEPH_CRYPTO_AES256KRB5`) is AES256-CTS-HMAC-SHA384-192 with a 32-byte key. So
the gateway's key loses both the longer key and the HMAC integrity. It is the
key type every daemon used before 19.2.6 and is still in `ALLOWED_CIPHERS`, not
a new weak mode. Exposure is limited to the `client.nvmeof.*` entity, whose
caps are `mon profile rbd` / `osd profile rbd`.

A gateway already deployed with an `aes256k` key has its key rotated to `aes`
on its next deploy, so a failed nvmeof service heals itself on redeploy rather
than needing manual cephx surgery. That rotation keys on daemon type, not on
what the running image supports, so redeploying a gateway whose image does
understand `aes256k` downgrades its key too.

## Upgrade notes

Clusters without an NVMe-oF service: nothing to do.

If an nvmeof service is already stuck from a 19.2.6 or later deploy, redeploy
it once after the upgrade:

```
ceph orch redeploy nvmeof.<service>
```

The gateway's key is rotated to a type its image supports and the service comes
up.
