## Justification (public)

Customer request. When RGW refuses a request because a rate limit was hit, the
client is told only that it was refused, not when it may try again. Clients
have to guess, and a client that guesses badly either hammers the gateway or
waits far longer than necessary.

This adds a `Retry-After` header to rate-limited responses, carrying the number
of seconds until the request would actually be allowed through, computed from
the current token-bucket state.

## Justification (internal)

cobaltcore-dev/cloud-storage#585.

Taken from upstream main. All three commits are merged upstream in main and
none of them has an upstream squid backport, so there is no upstream stable
branch to sync with later.

### Why three commits and not one

The request was only for the `Retry-After` header, which is upstream commit
`3dae903c` (ceph/ceph#68210). That commit does not stand on its own on top of
squid. It was written against a rate limiter that squid does not have.

`3dae903c` rewrites all four `should_rate_limit_*` functions in
`src/rgw/rgw_ratelimit.h` to return a delay instead of a bool, and the versions
it rewrites are the ones left behind by two earlier upstream commits:

- `dae572d5` (ceph/ceph#64762, "rate limit for LIST & DELETE ops") introduced
  the `OpType` enum, the `list`/`del` token counters, the
  `should_rate_limit_list()` / `should_rate_limit_delete()` functions, the
  `max_list_ops` / `max_delete_ops` limits, and the `rgw_ratelimit_interval`
  config option. `3dae903c` rewrites the two new functions and reads
  `rgw_ratelimit_interval` in all four of them to work out the delay.
- `91e9f00a` (ceph/ceph#66509, "ops large budget ... max_ops set to 0") added
  the `if (*_ops() > 0)` guards that keep the token counters from going
  negative. `3dae903c` carries those guards forward.

Two alternatives were tried and kept on scratch branches for comparison:

- `backport/585-2` — `3dae903c` alone on top of squid. It applies, but only
  after being hand-rewritten: `rgw_ratelimit_interval` does not exist in squid,
  so the interval had to become a downstream-only
  `static constexpr int64_t ratelimit_interval_seconds = 60`; the entire
  LIST/DELETE half of the change had to be dropped, so the header would only
  ever be computed for the read and write buckets; the `should_rate_limit()`
  signature had to be reverted to squid's `bool is_read` form; and the test file
  came over with 1 of the 43 new upstream tests (25 tests in the file instead of
  67). The result is a downstream invention that diverges from upstream in the
  exact file the next sync will touch.
- `backport/585-3` — `91e9f00a` alone on top of squid. Conflicts in
  `src/rgw/rgw_ratelimit.h` and `src/test/rgw/test_rgw_ratelimit.cc`, for the
  same reason: it patches the LIST/DELETE functions that `dae572d5` introduced.

Picking all three in upstream order instead costs two extra commits and buys:
`91e9f00a` and `3dae903c` apply byte-for-byte identically to upstream (verified
by interdiff), only `dae572d5` needs conflict resolution and only in mechanical
ways, the file ends up with all 67 upstream tests, and `rgw_ratelimit.h` stays
identical to upstream main so future syncs are a no-op there.

The cost is that the backport is wider than asked: it also brings the LIST and
DELETE rate limits, which are a feature in their own right. They are inert
unless an operator configures them — see Behavior change.

## Risk notes

**blast: availability** — the rate limiter decides whether a client request is
served at all, so a mistake here either refuses traffic that should be served
or stops refusing traffic that should be capped. No object data is at risk,
which is why this is availability and not data-loss. Two things keep the
exposure narrow:

- `rgw_ratelimit_interval` defaults to 60, which is the value squid had
  hardcoded, so the token-bucket arithmetic is unchanged out of the box.
- `max_list_ops` and `max_delete_ops` default to 0, and `op_type()` only
  classifies a request as `List` or `Delete` when the corresponding limit is
  greater than 0. With both unset, every request is classified exactly as
  before. An existing deployment that upgrades and changes nothing sees no
  change in which requests are rate limited.

One item deserves attention beyond this backport, described under Upgrade
notes: `dae572d5` bumps `RGWRateLimitInfo` to struct_v 2 while leaving the
compat version at 1, and inserts the two new fields in the middle of the
encoding rather than appending them.

**conflict: trivial** — three conflicts, all in `dae572d5`, none of them
touching logic:

- `doc/radosgw/admin.rst` — indentation drift. Squid indents the continuation
  lines of the `radosgw-admin ratelimit set --ratelimit-scope=bucket` example
  one column further than main does. The two new `--max-list-ops` /
  `--max-delete-ops` lines were added at squid's indentation.
- `src/common/options/rgw.yaml.in` — upstream inserts `rgw_ratelimit_interval`
  between options squid does not have (`rgw_d4n_backend_address`,
  `rgw_bucket_eexist_override`, `rgw_redis_connection_pool_size`), so the
  surrounding context did not exist. Only `rgw_ratelimit_interval` was added,
  appended at the end of the file; none of the neighbouring options were pulled
  in.
- `src/rgw/rgw_rest_ratelimit.cc` — the include block differs. Upstream places
  the new `#include "rgw_op.h"` after `rgw_process_env.h`, which squid's copy of
  the file does not include, because squid does not have `de90732`
  ("RGW/standalone: refactor RGWPeriodConfig with configstore") or `09383ab`
  ("RGW/standalone: review fixes"). The include was placed after squid's
  existing includes instead. The same two missing commits also explain why the
  surrounding context reads `period_config.write(...)` downstream where
  upstream reads `cfgstore->write_period_config(...)`; those are context lines,
  not part of the patch, and were left alone.

One further adaptation was applied by git and is not recorded in the commit
message: upstream's `src/rgw/radosgw-admin/radosgw-admin.cc` does not exist in
squid, where the file is still `src/rgw/rgw_admin.cc`. Rename detection mapped
it, and the resulting patch is byte-identical to upstream's (verified by
interdiff).

The other two picks, `91e9f00a` and `3dae903c`, needed no resolution at all
once `dae572d5` was in place; both are byte-identical to upstream.

**coverage: partial** — 43 new unit tests, the full upstream set: the test file
goes from 24 to 67 tests, matching upstream `3dae903c` exactly, with nothing
dropped or adapted. They cover the token arithmetic thoroughly:

- `compute_delay()` directly, including the disabled-limit and
  non-positive-deficit paths that return 0, and ceil-division at interval 1 and
  interval 100.
- LIST and DELETE rejection, giveback and refill, at both the `RateLimiter` and
  `RateLimiterEntry` level.
- Cross-dimension isolation: a LIST limit does not consume read, write or delete
  tokens, and vice versa, for every pair.
- The negative-budget regression from `91e9f00a`, for read, write, list and
  delete.
- `qa/tasks/radosgw_admin_rest.py` gains coverage of `max-list-ops` and
  `max-delete-ops` through the admin REST API.

What is not covered, and why this is partial rather than strong:

- Nothing asserts that the `Retry-After` header actually reaches the client.
  `dump_header()` in `abort_early()` (`src/rgw/rgw_rest.cc:716`) and the
  threading of the delay through `req_state::ratelimit_retry_after` in
  `src/rgw/rgw_process.cc` are untested. The unit tests stop at the value
  `should_rate_limit()` returns. This is the part the customer asked for, and
  it is the part with no automated check. Upstream has none either.
- LIST classification is a substring match on the query string for
  `list-type=`, `prefix=` or `delimiter=`. A plain `GET /bucket` with no query
  parameters is not recognised as a listing and still counts against
  `max_read_ops`. This is upstream behaviour, and it is neither tested nor
  documented upstream.
- The branch has not been built or had its unit tests executed yet. Before the
  PR: build and run `unittest_rgw_ratelimit`, and add a functional check that a
  rate-limited request carries `Retry-After` with a plausible value.

## Behavior change

**`Retry-After` on rate-limited responses.** A request refused with
`-ERR_RATE_LIMITED` still returns HTTP 503 with the S3 error code `SlowDown`,
unchanged, but now also carries a `Retry-After` header giving the number of
seconds until the token bucket has recovered enough for the request to pass,
with a floor of 1 second. Where both the user and the bucket limit are hit, the
user delay is reported. Operators who need `429 Too Many Requests` instead of
503 can remap it at the load balancer; the status code itself is deliberately
unchanged, as AWS S3 also answers 503 `SlowDown`.

**Two new rate-limit dimensions, both off by default.** `max_list_ops` and
`max_delete_ops` join the existing read and write limits, settable per user,
per bucket and globally, via `radosgw-admin ratelimit set
--max-list-ops=/--max-delete-ops=`, the admin REST API and the global period
config. Both default to 0, meaning unlimited.

They change how requests are counted once set, and this is the one thing to be
aware of:

- Setting `max_list_ops` moves bucket listings out of the read-ops bucket. A
  `GET` whose query string contains `list-type=`, `prefix=` or `delimiter=` is
  then counted against `max_list_ops` and no longer against `max_read_ops`. An
  operator who was capping listings indirectly through `max_read_ops` will find
  that cap no longer applies to them.
- Setting `max_delete_ops` likewise moves `DELETE` requests out of the
  write-ops bucket.
- A listing without any of those three query parameters is still counted as a
  read.

**New config option `rgw_ratelimit_interval`**, default 60, minimum 1, startup
only. This makes configurable the accumulation window that was previously
hardcoded to 60 seconds. The default reproduces the old behaviour exactly. It
sets both the token replenishment window and the divisor in the `Retry-After`
calculation, so shortening it makes limits refill faster and the advertised
delays shorter.

The `radosgw-admin` help text for the existing `--max-read-ops`,
`--max-read-bytes`, `--max-write-ops` and `--max-write-bytes` options now says
"per accumulation interval" rather than "per minute", since the interval is no
longer fixed at a minute.

## Upgrade notes

No migration and no action required. `max_list_ops` and `max_delete_ops`
default to 0 and `rgw_ratelimit_interval` defaults to the previously hardcoded
60 seconds, so an upgraded gateway rate limits exactly as before until an
operator sets one of the new values.

**One caveat for mixed-version and rollback windows.** `dae572d5` bumps the
`RGWRateLimitInfo` encoding from struct_v 1 to 2 and inserts `max_list_ops` and
`max_delete_ops` *between* `max_read_ops` and `max_write_bytes`, while leaving
the compat version at 1:

    ENCODE_START(2, 1, bl);

Because the compat version stayed at 1, a gateway running the older code does
not reject a v2-encoded blob. `DECODE_START(1, bl)` only throws when
`struct_compat > 1`, so it proceeds and reads the two new fields as
`max_write_bytes` and `max_read_bytes`, shifting every field after them. It
does not fail loudly; it silently applies wrong limits.

`RGWRateLimitInfo` is persisted in the `user.rgw.ratelimit` attribute on users
and buckets, and in the realm period config for the global limits, which
replicates across a multisite realm. So the exposure is:

- Setting any rate limit with the new `radosgw-admin` or admin REST API while
  older gateways are still running in the same cluster.
- Setting a global rate limit in a multisite realm where another zone has not
  been upgraded.
- Rolling back to the previous release after any rate limit has been written.

Recommended sequence:

1. Upgrade all RGW instances in the realm, including every multisite zone,
   before changing any rate limit.
2. Do not set `max_list_ops` or `max_delete_ops` until the upgrade is complete
   everywhere.
3. If a rollback is needed after rate limits have been written, re-set them
   with the older `radosgw-admin` so they are re-encoded as struct_v 1.

This is upstream's encoding, not a downstream change, and it is kept as-is so
`rgw_ratelimit.h` and `rgw_common.h` stay in sync with upstream main. It is
worth raising upstream.

To adopt the new limits:

    radosgw-admin ratelimit set --ratelimit-scope=user --uid=<uid> --max-list-ops=100
    radosgw-admin ratelimit set --ratelimit-scope=user --uid=<uid> --max-delete-ops=100
    radosgw-admin ratelimit enable --ratelimit-scope=user --uid=<uid>

Changing `rgw_ratelimit_interval` requires an RGW restart; it is a startup
option.
